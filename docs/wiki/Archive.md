## Частная резервная копия

Отдельно от публичного Git сохранены полный bucket S3 с manifest и SHA-256, custom-format дампы шести PostgreSQL-баз, глобальные роли, два Redis RDB, runtime-конфигурация и Git bundles всех исходных репозиториев. Архив рабочего каталога сохраняет частные операционные материалы; зависимости и пересобираемые кэши не нужны для восстановления исходников.

Базы выгружены онлайн: каждый `pg_dump` согласован внутри своей базы, общего атомарного снимка PostgreSQL + Redis + S3 не заявляется. На протяжении копирования S3 каталог объектов не менялся. Дампы PostgreSQL проверены реальным восстановлением во временные базы; RDB проверяются штатным Redis checker. Контрольные суммы скачанных файлов сверяются с источником. Подробные отчёты находятся в частной резервной копии.

## Восстановление

1. Сначала подготовьте изолированное окружение и свои секреты по `.env.example`.
2. Используйте версии PostgreSQL/Redis, совместимые с сохранёнными дампами; исходный production использует PostgreSQL 18.3 и Redis 8.2.9.
3. Проверьте роли и восстановите PostgreSQL custom dumps через `pg_restore`.
4. Восстановите долговечный Redis; решение о переносе кэша принимайте отдельно.
5. Верните S3-объекты под исходными ключами с метаданными из manifest и приватными правами.
6. Подключите собственные домены, S3 и SMTP. До включения worker и почты проверьте ожидающие задания.
7. Запустите health checks и пользовательские сценарии, затем открывайте доступ.

Файл `globals.sql` и runtime `.env` содержат чувствительные сведения и предназначены только для частного архива. Они не входят в публичный репозиторий или релиз.
