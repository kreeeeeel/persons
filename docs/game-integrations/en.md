# Game integrations and dynamic properties

The match dialog centers the pixel hero icon, name and outcome tag. Stat blocks center the value above its label; hero/building damage use HD/TD with full title descriptions. KDA precedes a Dota-style 3×2 inventory with an unlabeled neutral slot. Known acquisition clocks appear on items; unknown damage/timing remains unavailable. The external match link sits beside Close and the timestamp at the bottom right. Optional source fields are persisted by V22 and exposed by generated contracts. Fixture support is not verification of the live Dotabuff layout. Feed events show the page avatar/name and a secondary “played a match in [icon] Dota2 · time” label using shared ContentTime. Spacing within and between game events uses a cumulative factor of 2.25, including the additional 1.5 reduction requested during review.

The full architecture and examples are in [the Russian document](ru.md).

The backend dynamic-properties library owns its OpenAPI contract, typed declarations, validation, administrative controllers, Redis reconciliation, revisions and notifications. Applications declare private DynProperty fields. Startup registers declarations for the stable spring.application.name scope, restores memory before readiness and subscribes to changes. Normal reads never access Redis. A changed type/default/schema resets to the new default; description changes retain overrides. Removing code removes only the starting scope's ownership. A reconnect restores a complete snapshot, including missed deletions.

A dedicated properties-redis service uses AOF, appendfsync everysec, noeviction and a persistent volume. Configure DYNAMIC_PROPERTIES_REDIS_HOST/PORT/PASSWORD/PREFIX. Explicit memory storage is test-only and rejected in production. Changing a property's type requires coordinating consumer versions.

The separate frontend library is configured with DYNAMIC_PROPERTIES_BASE_URL (defaults to PERSON_BASE_URL). Next registers public frontend.* definitions with a service JWT; browsers cannot register definitions. Backend-owned handles use external(). Node and browser caches consume snapshots and SSE. React reads typed handles through useDynProperty. SSR snapshots remain stable during hydration. No value polling occurs; reconnects retain the latest known values. The BFF validates Origin and keeps service credentials server-side. Library error mapping preserves authorization and optimistic-conflict responses across generated clients.

dotabuff-integration owns HTTP, parsing, Steam ID resolution and provider domain models; it does not own SQL or scheduling. person-worker uses com.persons.personworker packages and GameIntegration implementations. It schedules each enabled integration at its actual interval and replaces the future on a property notification. There is no short polling tick. A single execution thread prevents overlap; JPA leases coordinate replicas. The legacy GitLab remote can remain personal-worker.git, with a CI path alias for upstream triggers.

The worker processes five eligible Steam-linked profiles and one history page per profile per run. Cursor/backfill progress persists. Numeric Steam IDs and validated Steam vanity XML are supported. HTTP uses bounded responses, timeouts and spacing; redirects/challenges are not bypassed. New matches and items are saved with cursor progress after validating the lease and current linkage. The per-person match key is idempotent. A complete scan retains a one-day overlap; source/date changes restart scanning without deleting stored matches. Failed requests retain the cursor and honor Retry-After or a five-minute retry.

Properties: games.dotabuff.enabled defaults false; importFrom defaults 2026-10-22T00:00:00Z; pollIntervalSeconds defaults 300 and accepts 60–86400. frontend.person.games.enabled defaults true.

Provider-specific implementations supply loading, card, details and their own empty illustration/title/description through the frontend GameIntegration interface. Shared GameHistory provides pagination and states. The profile section is Games; service tabs reuse SegmentedTabs, scroll horizontally and hide the scrollbar. Match dialogs link to DotaBuff. The feed reuses the same card beneath the page identity inside a transparent wrapper. Signed-in users can access the feed from the landing header. Shared scrollbar-gutter compensation prevents modal scroll locking from shifting the page.

The library contract provides admin list/update, public snapshots, SSE and authenticated server registration. Person references this contract. Game API: GET /v1/persons/{id}/games/dota2/matches and GET /v1/games/dota2/events, with page/size (maximum 60). Hidden/deleted pages are excluded.

Tests cover parser/HTTP failure fixtures, typed values, validation, real Redis Lua/PubSub/autoconfiguration, leases, cursor progress, idempotency, API visibility, SSR, SSE and frontend dialogs. Redis tests require REDIS_TEST_HOST/PORT. Live DotaBuff returns HTTP 403 in this environment; the parser has been verified against controlled fixtures, not a live account. Imports stay disabled until an authorized accessible source and current markup can be verified.

The server aggregate `GET /v1/feed` applies shared sorting, filters and pagination to Dota/CS matches and existing publications without a per-source first-page cap. See [real directory and feed data](../community-data/en.md).

Local preview: start-community-preview.ps1 provides the mock API on 4310 and apps on 3000–3002. Match fixtures belong to the mock transport, not UI components. Open /ru/person/krel?preview=integrations, or another profile's Games tab for the empty state.

## Leetify / Counter-Strike 2

`backend/libs/lettify-integration` owns `LeetifyClient`: profile, user history, match details by UUID and by data-source/ID. It uses the [official Public API](https://api-public-docs.cs-prod.leetify.com/), server-only `_leetify_key`, bounded responses, request spacing, timeouts and Retry-After handling.

The worker resolves the linked Steam profile and upserts the latest available match window into a persistent archive. Public API does not document archive pagination; the first import contains only its available window, and subsequent imports accumulate every observed match. Leaving the latest window does not delete an archived match. Private/404 profiles clear the archive, and a changed Steam account starts a separate history. After 24 hours without successful profile validation, the archive is hidden without deletion until the next successful refresh.

Private dynamic properties: `games.leetify.enabled=false`, `games.leetify.importFrom=2026-10-23T00:00:00Z`, `games.leetify.pollIntervalSeconds=300` (60–86400). Configure the optional `LEETIFY_API_KEY` only on the worker. The CMS switch directly controls synchronization; the redundant storage switch has been removed. The application persists the match archive at the project owner's request; [provider guidelines](https://leetify.com/blog/leetify-api-developer-guidelines/) still apply to stored data. Mock preview does not contact Leetify.

Generated API routes: `GET /v1/persons/{id}/games/cs2/matches`, `GET /v1/games/cs2/events`, with page/size (maximum 60). Map, result, score, K/D/A, KD, ADR (`dpr`), HS kill percentage and historical rank come from provider responses. Rank type 11 is Premier, 12 is per-map Competitive, 7 is Wingman. Current profile ranks never replace historical values. Duration, historical FACEIT Elo and Personal Performance are generally absent from Public API; absent values remain unknown. Leetify Rating is not Personal Performance. Personal Performance uses display units and the provider's tag colors/thresholds.

For share-code detail lookup, the client normalizes history sources `matchmaking_competitive` and `matchmaking_wingman` to `matchmaking`: `/v2/matches/{dataSource}/{dataSourceId}` uses the common source name. UUID lookups need no normalization. Public API history covers recent matches; the profile's total count does not mean that the entire archive is returned.

The second Games tab is Leetify. Profile history and feed reuse cards/dialogs with map emblems, result followed by score, rank images, FACEIT level/Elo, KDA, HS and Personal Performance. The separator uses the normal text color and the score uses secondary text. Wingman uses its own rank emblems; FACEIT level images come from the official FACEIT help center. The literal `ELO` suffix appears only on cards. Preview has 18 synthetic CS matches, multiple modes/outcomes and missing data. Open the profile preview above and select Leetify.

## JPA and validation

Dota cards show outcome, separator and the final score from the player's team perspective. Optional `score`/`opponentScore` pass through the parser, JPA, migration V25 and the shared history/feed API. Missing source scores and old records remain unknown. History rank images are two thirds of their former size; FACEIT keeps square proportions. Visited game tabs retain their data and height, while inactive tabs do not trigger automatic pagination.

Production persistence uses Spring Data JpaRepository/JpaSpecificationExecutor, Criteria API and JPQL. API/worker entities are shared through maintenance. There are no production JDBC templates or native SQL queries. The heterogeneous publication catalog uses Hibernate Criteria unions. JPA locks preserve queue/lease concurrency, and archive/cursor changes commit atomically. Flyway still owns DDL.

`node scripts/check-persistence.mjs` checks backend production and test sources through check-backend.ps1 and backend CI. Test fixtures also use JPA. For catalog PostgreSQL tests set PUBLICATIONS_TEST_DB_URL/USER/PASSWORD; worker locking tests use WORKER_POSTGRES_TEST_URL (tests/tests credentials). To run the other worker integration tests against PostgreSQL, set SPRING_DATASOURCE_URL/USERNAME/PASSWORD and WORKER_TEST_DIALECT=org.hibernate.dialect.PostgreSQLDialect. Run Gradle build/ktlintCheck, frontend npm run check, and E2E_MOCK_PREVIEW=true npx playwright test tests/e2e/leetify-preview.spec.ts against the running preview.

## Production provider recovery

Dota imports now use the public OpenDota API because DotaBuff rejects production requests. The existing games.dotabuff settings prefix is retained for compatibility. The client reads 100-match pages with offset, fetches player details and refreshes hero/item dictionaries hourly. Lease, cursor, importFrom and deduplication remain in place; absent metrics stay absent. Cards identify and link to OpenDota. HTTPS uses TLS 1.2 with normal certificate and hostname validation. Apache HttpClient, pinned by the project BOM, tries all DNS addresses on TCP/TLS failures, with a five-second connection/handshake limit per address. Provider response timeouts, response-size bounds and request intervals remain enforced. HTTP 403/404/429 remain explicit failures.

Leetify imports accumulate all observed matches in the database and update existing IDs without duplicates. Matches leaving the provider’s latest-100 window remain archived. A private/unavailable profile clears the archive; changing Steam accounts starts a separate history. The archive is temporarily hidden after 24 hours without successful profile validation, then restored by the next successful refresh. Set games.leetify.importFrom to 1970-01-01T00:00:00Z to import the full available initial window. The CMS games.leetify.enabled setting now controls scheduling directly; the separate storage approval switch was removed at the project owner’s request. Provider guidelines still apply to stored data. An optional API key raises request limits; anonymous public API calls are supported.
