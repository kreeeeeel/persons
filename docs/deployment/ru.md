# Деплой «Те ещё люди»

Переключение между MinIO и внешним S3, префиксы файлов и очистка описаны в
[инструкции хранилища](storage_ru.md).

Новые gateway/restrictions, Redis и перенос прежних блокировок: [порядок обновления](restrictions_ru.md).

Группа: https://gitlab.com/te-eshche-lyudi. Сервисы и библиотеки — отдельные приватные проекты в подгруппах `backend` и `frontend`. Общий Docker, CI и деплой находятся в [infrastructure](https://gitlab.com/te-eshche-lyudi/infrastructure). Runtime-секреты хранятся в `shared/.env` на VDS; SSH-параметры деплоя — в защищённых переменных CI. Секреты не включаются в Git.

## Pipeline

Каждый проект включает `ci/component.yml` из infrastructure и запускает общий pipeline с точным SHA изменённого компонента через проверяемые pipeline inputs. Статус возвращается через `strategy: mirror`. `resolve` один раз фиксирует SHA infrastructure и компонентов в `workspace.lock`. Все проверки и сборки используют этот снимок. `RELEASE_SHA` — Git hash lock; он обозначает всю выкладку, а не общий тег всех контейнеров.

`ci/build-inputs.mjs` описывает зависимости образов: исходники своего проекта, общие библиотеки, API-контракты, Gradle-конфигурацию, Dockerfile и скрипт сборки. Из этих входов вычисляется отдельный неизменяемый тег каждого сервиса. Если проверенный образ с таким тегом уже есть в Registry, повторная проверка и сборка этого же содержимого не запускаются. Ошибки авторизации или связи с Registry останавливают pipeline: они не считаются отсутствием образов. `ci/verified-images.json` связывает входы последней проверенной полной сборки с её прежними тегами, чтобы переход на новую схему не требовал пересборки. Этот файл не нужно обновлять после каждой выкладки.

На основании плана создаётся [динамический child pipeline](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/#dynamic-child-pipelines) только с нужными jobs. Lock и перечень образов передаются в сгенерированной конфигурации; платные cross-pipeline artifact dependencies не требуются. `operations` всегда проверяет инфраструктуру, включая тесты выбора сборок, deploy, op и Nginx.

| Изменение | Что собирается |
| --- | --- |
| Только `frontend/person` | Только `person-web` |
| Общая тема, UI, i18n, редактор фото | Три фронтенда |
| `person-domain` | Публичный сайт и CMS |
| Реализация API без изменения контракта | Соответствующий backend |
| API-контракт | Его backend и потребители контракта |
| `person/app/maintenance` | person и person-worker |
| Брендовые ассеты | Фронтенды и загрузчик assets; сервер MinIO сохраняется |
| Dockerfile сервера MinIO | Только MinIO и проверка хранилища |
| Документация infrastructure и CI/deploy-скрипты | Проверки инфраструктуры; образы приложений сохраняются |

Для изменившихся фронтендов отдельная job генерирует только TypeScript-клиенты через `generateClients`, без компиляции серверных приложений. Результат кэшируется по контрактам и версии генератора. В выбранных сборках сохранены ktlint, unit/integration-тесты, ESLint, Stylelint, Prettier, TypeScript и production build. Публикация разрешена только для основных веток; storage-образы сначала публикуются как кандидаты и получают проверенный тег только после успешного S3 smoke test. Каждая публикация скачивает артефакты только своего приложения.

Образ инструментов (JDK 21, Gradle 8.14.3, Node 24.11.1) также переиспользуется по содержимому Dockerfile. После обновления версий базовых образов измените соответствующий Dockerfile; для принудительного обновления плавающего базового тега достаточно изменить этот файл. При изменении команд сборки меняйте `ci/build-backend.sh`, `ci/build-frontend.sh` или `ci/build-clients.sh`: они входят в ключи кэша. При добавлении новых зависимостей обновляйте граф и его тесты.

В Settings → CI/CD → Job token permissions у infrastructure разрешены входящие job tokens группы `te-eshche-lyudi` для запуска downstream pipeline и чтения результатов jobs; у компонентов — только проекта infrastructure для чтения их кода. Пользователь, запустивший pipeline, также должен иметь доступ к этим проектам. Постоянные токены для сборки не нужны. Чтобы обновить общую CI-логику, измените infrastructure; API-клиенты по-прежнему генерируются из контрактов, npm/Maven-пакеты в Registry автоматически не публикуются.

Pipeline использует project runner «Persons desktop Docker» с тегом `persons-local`, зарегистрированный в существующем контейнере GitLab Runner на ПК. Он ограничен infrastructure и двумя одновременными задачами. Docker executor поддерживает Docker-in-Docker с TLS (`/certs/client`, privileged service); компьютер и Docker должны работать во время CI. Остальные зарегистрированные runners не изменяются. GitLab Registry используется через автоматические `CI_REGISTRY_*`, никаких пользовательских секретов для сборки не требуется. Jobs деплоя появляются только после заполнения серверных переменных и запускаются вручную. Одновременные выкладки сериализованы через `resource_group: production`.

MinIO и его клиент собираются из официальных исходников с закреплёнными commit SHA через Go 1.27.2: старые vendor-образы недоступны для чистого скачивания. Сервер использует [официальный security-релиз 2025-10-15](https://github.com/minio/minio/releases/tag/RELEASE.2025-10-15T17-29-55Z), клиент — исходники релиза 2025-04-16. Лицензии включены в образы. Production скачивает оба готовых образа из Registry проекта. Перед обновлением существующего S3-хранилища обязательно сохранить резервную копию данных; текущая локальная база и volume при настройке CI не переинициализируются.

## Когда будут хосты и домены

1. Подготовить Linux VDS с Docker Engine, Compose **2.24.4 или новее**, `tar`, `stat` и SSH. Выделить каталог, например `/opt/persons`, с правами пользователя деплоя. Пользователь должен иметь доступ к Docker. Хостовые порты базы, S3, API и фронтендов привязаны к loopback.
2. Вручную создать `/opt/persons/shared/.env` с правами `0600`, используя перечень ключей из корневого `.env.example`. Заменить локальные значения уникальными секретами и фактическими HTTPS URL. Этот файл pipeline не создаёт и не перезаписывает. SMTP должен быть настроен явно: production не использует Mailpit по умолчанию.
3. Настроить хостовый Nginx по [инструкции для трёх доменов](nginx_ru.md): основной домен → `127.0.0.1:3002`, `id.` → `:3000`, `cms.` → `:3001`. Production Compose отключает локальный gateway и открывает эти порты только на loopback. `SESSION_COOKIE_DOMAIN` задаёт общий корневой домен для защищённой HttpOnly-cookie. Все три публичных URL должны использовать HTTPS и входить в этот домен; конфигурация проверяется при запуске. Не публиковать backend и административные панели MinIO/PostgreSQL напрямую.
4. На VDS один раз выполнить `docker login registry.gitlab.com` с отдельным GitLab deploy token с правом `read_registry`. Токен не передаётся в репозиторий или скрипты pipeline.
5. В Settings → CI/CD → Variables проекта infrastructure добавить **protected** переменные с environment scope **production**: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`, при необходимости `DEPLOY_PORT` (по умолчанию 22). Добавить **file** variables `DEPLOY_SSH_KEY` и `DEPLOY_KNOWN_HOSTS` с теми же ограничениями. Секреты выкладки доступны только deploy job, а не проверкам исходного кода компонентов. Fingerprint SSH-хоста проверить отдельно. Скрипт всегда использует `StrictHostKeyChecking=yes`.
6. Защитить основную ветку и доступ к environment `production` в соответствии с возможностями вашего тарифа. После настройки задать обычную переменную `DEPLOY_ENABLED=true` (scope `*`), чтобы включить ручной deploy job. Секреты со scope production не используются при вычислении rules. Запустить pipeline основной ветки; после проверок и публикации запустить ручной `deploy`.

Скрипт передаёт архив конфигурации с `workspace.lock` и `images.env`, без серверного `.env`. Для каждого сервиса сравнивается hash разрешённой Compose-конфигурации с предыдущей успешной выкладкой. Относительные bind mounts сравниваются без привязки к каталогу release. Скачиваются и обновляются только изменившиеся сервисы, последовательно, с `--no-deps` и ожиданием health check. Неизменившиеся здоровые контейнеры продолжают работать; отсутствующие или нездоровые восстанавливаются. При первой выкладке запускается весь стек. Изменения runtime-параметров и ресурсного профиля тоже учитываются. После успешных health checks обновляет `current` и сохраняет ссылку `previous`. Базы и S3 используют постоянные volumes проекта `persons-production`. Ошибка не удаляет данные. Скрипт не откатывает Flyway автоматически: перед изменениями схемы нужны резервная копия и проверка совместимости. Для повторной попытки того же SHA сначала осмотреть оставшийся `releases/<SHA>`; скрипт не перезаписывает существующий release.

## Ограниченный режим для небольшого VDS

Для согласованного запуска на VDS с 2 ГБ RAM подготовьте дисковый swap (например, 4 ГБ), затем создайте `/opt/persons/shared/resource-profile` с единственной строкой `small`. Файл не содержит секретов и сохраняется между релизами. Без него используется стандартный режим.

В этом режиме `docker/compose.small.yaml` ограничивает heap JVM и Node.js, размер PostgreSQL buffers и пулов соединений. Учитывается также нативная память JVM; контейнерам разрешён swap. Скрипт скачивает образы по одному и запускает сервисы последовательно с ожиданием health check. Настройки лимитов остаются в Git, а выбор режима — на сервере. Это начальная конфигурация для малой нагрузки; контролируйте `docker stats`, swap, задержки и счётчики OOM после выкладки. Обработка видео и одновременные загрузки потребуют отдельной проверки под реальной нагрузкой.

Вернуться к стандартным ресурсам после увеличения VDS: записать `standard` в `shared/resource-profile` и выполнить следующую выкладку. Данные PostgreSQL и S3 используют те же volumes.

## Доставка образов на сервер с ограниченным доступом к Registry

Если сервер не может скачать образы, задайте protected-переменную `DEPLOY_TRANSFER_IMAGES=true` со scope `production`. Deploy job скачает из Registry только отсутствующие на VDS образы из проверенного `images.env`, передаст их по SSH и сверит ID загруженных образов. Уже установленные образы сохраняются; при внешнем S3 локальный MinIO не передаётся. Используется прежний ключ деплоя и обязательная проверка ключа хоста. Runtime `.env` не передаётся. Compose скачивает только отсутствующие образы с `--policy missing`, поскольку теги закреплены по входным данным сборки.

Для сетей, где обычное SSH-соединение зависает на обмене идентификацией, доступна protected-переменная `DEPLOY_SSH_SERVER_FIRST=true` со scope `production`. Bash-прокси сначала передаёт идентификацию сервера, затем пропускает поток SSH без изменений. Ожидание идентификации ограничено восемью секундами с тремя попытками; установление SSH ограничено 35 секундами. Проверки образов, копирование и выкладка используют одно соединение OpenSSH, которое сохраняется до минуты между командами. Проверка ключа, аутентификация и шифрование остаются в OpenSSH. Обе настройки по умолчанию выключены.

Deploy job устанавливает GNU coreutils: в используемом окружении Alpine SSH зависал при работе прокси с BusyBox `cat`, а с GNU coreutils полное соединение с VDS прошло успешно. Отдельный тест проверяет передачу данных в обе стороны без ожидания закрытия stdin.

Проверки: `sh scripts/tests/transfer-images.test.sh` и `node --test ci/tests/ssh-server-first.test.mjs` (в Linux). Они проверяют передачу только отсутствующего образа, пропуск MinIO для внешнего S3, отказ при несовпадении ID или некорректном manifest, порядок SSH-обмена и запрет метасимволов в адресе прокси.

## Выдать администратора

После первой успешной выкладки один раз установить команду:

```sh
sudo sh /opt/persons/current/scripts/install-op.sh /opt/persons
op friend@example.com
```

Пользователь команды должен иметь доступ к Docker. Команда находит существующий подтверждённый активный аккаунт по почте без учёта регистра, выдаёт `ADMIN` и завершает действующие сессии. Пользователю нужно войти снова. Повторный запуск для администратора ничего не меняет. Неизвестная почта или заблокированный аккаунт дают ошибку; аккаунты не создаются и не разблокируются. Скрипт установки не перезапишет уже существующий `/usr/local/bin/op`, например CLI другого приложения. Без установки: `sh /opt/persons/current/scripts/op friend@example.com`.

SQL использует psql-параметр `:'email'`, блокировку строк и одну транзакцию. Почта не вставляется в SQL конкатенацией; проверка покрывает апострофы и попытку SQL-инъекции. `PERSONS_ADMIN_EMAIL` остаётся только механизмом первоначальной загрузки; для операционной выдачи прав он не нужен.

## Яндекс ID

Authorization Code, PKCE S256, одноразовый `state`, привязка к браузеру и защита от автоматического объединения аккаунтов уже реализованы и покрыты тестами. Реальная авторизация не проверена без реквизитов приложения. Когда будут домены, зарегистрировать приложение, выставить точный callback `https://<ID-host>/api/oauth/yandex/callback` и права `login:info`, `login:email`; заполнить `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI` только на сервере. Подробности — в [README](../../README.md#яндекс-id).

## Локальные проверки инфраструктуры

```sh
sh scripts/tests/op.test.sh
sh scripts/tests/nginx.test.sh
# Сначала задать временные IMAGE_PREFIX, RELEASE_SHA и runtime-переменные:
docker compose -f docker-compose.yaml -f docker/compose.production.yaml config --quiet
```

Тест `op` создаёт отдельный временный контейнер PostgreSQL без опубликованных портов и удаляет его после проверки. Рабочая база проекта не используется.

При изменении MinIO или assets CI запускает `scripts/tests/storage.test.sh` с кандидатами и неизменившимися проверенными образами. В отдельной Docker-сети он проверяет запуск S3, загрузку брендовых файлов, публичное чтение иллюстраций и запрет анонимного чтения аватаров. Контейнер не использует рабочие volumes и удаляется после проверки.

`node --test ci/tests/build-plan.test.mjs` проверяет выбор сборок, зависимости и повторное использование образов. `sh scripts/tests/deploy.test.sh` проверяет скрипт выкладки с имитацией Docker: отказ без конфигурации, ошибку health check, успешное переключение release, сохранность серверного `.env` и отказ перезаписывать существующий release.

Тест Nginx использует отдельный временный контейнер, генерирует тестовый сертификат и проверяет HTTP/ACME, HTTPS, маршрутизацию, заголовки реального IP и лимиты загрузки. Данные проекта и рабочие контейнеры не используются.

При `DEPLOY_TRANSFER_IMAGES=true` CI и VDS должны иметь Python 3.11 или новее. Перед загрузкой Docker проверяется SHA-256 переданного архива, после загрузки — SHA-256 конфигурации из повторно экспортированного образа. Конфигурация содержит хеши распакованных слоёв. Этот идентификатор одинаков для classic и containerd image store; поле Docker `.Id` между ними сравнивать нельзя. Тест передачи проверяет оба формата архива, неоднозначный manifest, повреждение передачи и несовпадение конфигурации.
