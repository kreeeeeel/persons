# Шлюз и перенос блокировок

BFF → gateway:8087 → ID:8081 или Person:8085. Gateway получает политику из Restrictions:8088. Restrictions владеет отдельной базой `restrictions` и версионным Redis-кэшем; ID и Person используют разные базы `id` и `person`. Redis доступен только внутри production-сети, защищён паролем и хранит исключительно воспроизводимый кэш, без AOF/снимков.

При недоступном Redis Restrictions читает PostgreSQL. При недоступной БД/ID/Restrictions шлюз возвращает 503 для операций с проверкой. Изменение или снятие запрета применяется сразу по версии записи; истечение проверяется по времени независимо от джобы. Worker отзывает просроченные записи через API владельца. Person сохраняет проверку ролей и владения контентом, но прежней runtime-зависимости от таблиц блокировок больше нет.

Запустите `./scripts/setup.ps1`: он допишет отсутствующие `PROJECT_GATEWAY_JWT_SECRET` и `REDIS_PASSWORD` в существующий локальный `.env`, сохранив остальные значения. При ручной production-настройке добавьте два случайных секрета в `shared/.env` с правами 0600. Не публикуйте его в CI-артефактах. BFF получают адреса `http://gateway:8087/id` и `http://gateway:8087/person`; секрет подписи шлюза получают только Gateway и Person.

На новом PostgreSQL-томе база Restrictions создаётся автоматически. На существующем production deployment-script создаёт только недостающую базу, запускает Restrictions для Flyway DDL, останавливает прежние Person/worker и выполняет `scripts/migrate-restrictions.sh DEPLOY_PATH`. Сценарий сохраняет резервную копию Person в `shared/migrations`, переносит причины, авторов, UUID, даты, отзыв и все области запрета, сверяет содержимое и ставит `shared/restrictions-migrated`. При ошибке прежние контейнеры запускаются обратно. Исходные таблицы и Flyway-история Person сохраняются; другие пользовательские данные не переносятся.

Для существующего локального окружения: остановите Person/worker; создайте базу `docker compose exec -T postgres createdb -U persons restrictions`, если её ещё нет; запустите `docker compose up -d --build restrictions`. Запустите migration-script из Linux/WSL: первым аргументом передайте отдельный абсолютный каталог с `shared/`, вторым — ID текущего PostgreSQL-контейнера. После проверки переноса запустите остальные сервисы `docker compose up --build -d`. Если старых таблиц нет, сценарий считает источник пустым. Непустая отличающаяся целевая база не перезаписывается. Повторный запуск без маркера проверяет совпадение содержимого.

Возврат на старую версию после начала новых изменений требует обратного переноса актуальных блокировок; один откат образов недостаточен. Не удаляйте тома или старые таблицы. На новом VDS копируйте текущие базы, конфигурацию, маркеры переноса и профиль внешнего S3; первоначальный архив до миграции S3 уже устарел.

Проверки: `node --test ci/tests/build-plan.test.mjs ci/tests/external-s3.test.mjs`; Linux `sh scripts/tests/deploy.test.sh`, `sh ci/tests/deploy-bundle.test.sh`, `sh scripts/tests/restrictions-migration.test.sh` (последнему нужен Docker Engine). Новые сервисы: `./gradlew build ktlintCheck`; CI отдельно проверяет PostgreSQL 18.3 и Redis 8.2.9. Тесты проверяют перенос, конкурентные изменения ролей/банов, немедленный отзыв кэша, 3 МБ chunked-загрузку и Range/206. Изменение только фронтенда не пересобирает и не перезапускает серверные сервисы.
