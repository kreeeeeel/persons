# Gateway and restriction ownership migration

BFF → gateway:8087 → ID:8081 or Person:8085. Gateway obtains policies from Restrictions:8088. Restrictions owns its `restrictions` database and revision-based Redis cache; ID and Person use separate `id` and `person` databases. Production Redis is private, password-protected, and stores reproducible cache only without AOF/snapshots.

Redis failures fall back to PostgreSQL. Database/ID/Restrictions failures return 503 for checked operations. Revision changes make edits and revocations immediate; expiry is enforced by clock independently of cleanup. Worker revokes expired records through the owner API. Person retains authorization and content ownership checks but no longer reads restriction tables at runtime.

Run `./scripts/setup.ps1` to append missing `PROJECT_GATEWAY_JWT_SECRET` and `REDIS_PASSWORD` to an existing local `.env`, preserving all other values. For production, add random secrets to `shared/.env` with mode 0600. Never include that file in artifacts. BFFs use `http://gateway:8087/id` and `http://gateway:8087/person`; only Gateway and Person receive the gateway signing secret.

Fresh PostgreSQL volumes create the Restrictions database automatically. Existing production upgrades create only a missing database, start Restrictions for Flyway DDL, stop legacy Person/worker writers, and run `scripts/migrate-restrictions.sh DEPLOY_PATH`. This backs up Person under `shared/migrations`, preserves reasons, creators, UUIDs, dates, revocation and scopes, verifies content, then writes `shared/restrictions-migrated`. Failure restarts the previous containers. Original tables and Person Flyway history remain intact; unrelated user data is not transferred.

For an existing local setup, stop Person/worker; create the database with `docker compose exec -T postgres createdb -U persons restrictions` if missing; start `docker compose up -d --build restrictions`. Run the migration script under Linux/WSL with an absolute deployment directory containing `shared/` as its first argument and the current PostgreSQL container ID as its second. After verifying migration, start the remaining services with `docker compose up --build -d`. Missing legacy tables mean an empty source. A differing nonempty destination is never overwritten. Without a marker, reruns verify content equality.

Rolling back after new restriction mutations requires reverse-transfer of current restrictions, not merely reverting images. Retain volumes and legacy tables. For the new VDS, copy current databases, runtime configuration, migration markers and external S3 profile; the initial pre-S3-migration archive is stale.

Checks: `node --test ci/tests/build-plan.test.mjs ci/tests/external-s3.test.mjs`; under Linux, `sh scripts/tests/deploy.test.sh`, `sh ci/tests/deploy-bundle.test.sh`, `sh scripts/tests/restrictions-migration.test.sh` (requires Docker Engine). New services use `./gradlew build ktlintCheck`; CI additionally tests PostgreSQL 18.3 and Redis 8.2.9. Tests cover migration, concurrent role/ban changes, immediate cache invalidation, a 3 MB chunked upload and Range/206. Frontend-only changes do not rebuild or restart backend services.
