# Фоновые задания и ленты

`backend/person-worker` — отдельный Spring Boot сервис с заданиями домена person. У него нет пользовательских API. Actuator health на внутреннем порту 8086 используется Docker; порт не опубликован на хост. `docker compose up --build -d` запускает воркер вместе с остальным проектом. Для просмотра состояния: `docker compose ps person-worker`, для диагностики: `docker compose logs --tail 100 person-worker`.

Общая Gradle-библиотека `backend/person/app/maintenance` содержит Flyway-миграции, конфигурацию S3 и хранилище рассчитанных итогов. API и воркер используют одну БД `person`; каждый сервис самостоятельно проверяет миграции при старте. Старые миграции перенесены без изменения содержимого и контрольных сумм.

## Расчёт оценок и репутации

Изменение или удаление оценки, создание персоны и согласованное создание, изменение или удаление займа помещают ID персоны в `person_aggregate_queue` в той же транзакции. Повторные изменения объединяются в одну запись. Миграция V6 ставит в очередь уже существующие персоны.

Каждые две секунды воркер берёт до 100 персон. Перед расчётом он блокирует строку персоны через `FOR UPDATE SKIP LOCKED`. API использует ту же строку и порядок блокировок. Поэтому изменение не теряется при одновременном расчёте, а несколько воркеров могут работать вместе. Итоги и удаление записи из очереди коммитятся одной транзакцией. При ошибке очередь сохраняется, а задание повторяется. Ошибка пишется в журнал.

`person_aggregates` хранит число и среднее оценок, число и прежний счёт займов, enum репутации и дату расчёта. `person_rating_option_totals` хранит счётчики настроенных эмодзи. GET-запросы читают эти таблицы, без расчёта среднего на лету. Собственная оценка сохраняется сразу. Пока идёт перерасчёт, `calculationPending=true`; сайт показывает вращающийся логотип и опрашивает профиль с интервалом две секунды. После ошибки опрос повторяется через пять секунд. Черновик комментария при обновлении итогов сохраняется.

Для репутации оценка нормируется в диапазон 0–100: `(средняя оценка − 1) / 4 × 100`. Подтверждённые и не удалённые займы получают значения: возвращает в срок — 100, с маленькой задержкой — 65, с большой задержкой — 25, не возвращает — 0. Старые `TRUST` и `DOUBT` соответствуют 100 и 0. Сначала считается среднее отдельно по каждому источнику, затем берётся 60% от оценок и 40% от займов. Если один источник отсутствует, второй определяет результат полностью. Хорошая репутация — от 70, средняя — от 40 до 70, плохая — ниже 40. При отсутствии обоих источников — `UNKNOWN`. Несогласованный текст отзыва не виден другим людям; его числовая оценка учитывается сразу.

## Ограничения и S3

Автоматические достижения за возраст страницы выдаются отдельной джобой каждые пять минут, пакетами до 500 выдач. [Правила годовщин, конкуренция, настройка и PostgreSQL-тесты](automatic-achievements_ru.md).

Каждые 30 секунд worker вызывает внутренний API сервиса Restrictions для отзыва истёкших ограничений порциями до 500 записей. Бессрочные и продлённые ограничения сохраняются. Worker не читает чужие таблицы блокировок; их владелец хранит отдельную БД и Redis-кэш. Restrictions независимо проверяет `expires_at` при каждом запросе: остановка воркера не продлевает бан.

Раз в минуту воркер удаляет из S3 удалённые медиа, файлы удалённых персон и незавершённые загрузки старше суток. Очередь `storage_garbage` учитывает время вывода файла из использования; старые записи без этой даты сохраняют суточный защитный интервал. Удаление идемпотентно; при ошибке S3 запись остаётся для следующей попытки. Новые загрузки и медиа на модерации защищены от очистки. Переменные окружения воркера: `DB_URL`, `DB_USER`, `DB_PASSWORD`, `PROJECT_INTERNAL_JWT_SECRET`, `RESTRICTIONS_BASE_URL`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`. Интервалы при необходимости задаются `AGGREGATES_DELAY`, `RESTRICTIONS_DELAY`, `MEDIA_CLEANUP_DELAY` в ISO-8601, например `PT2S`.

## Подгрузка лент

Серверная пагинация сохранена. Стена и комментарии медиа запрашиваются по 10 записей; остальные публичные ленты — по 12. Сортировка по дате и ID стабилизирует порядок записей с одинаковым временем. `useInfinitePersonData` добавляет страницы к уже загруженным записям, удаляет пересечения по ID и отменяет запрос при смене персоны или закрытии модального окна. `InfiniteFeedLoader` использует IntersectionObserver и общий `BrandLoader`; при ошибке уже загруженные записи остаются, появляется повтор той же страницы. Без IntersectionObserver доступна кнопка подгрузки. При `prefers-reduced-motion` логотип не вращается. Эти компоненты общие для сайта и CMS.

## Проверки

Из `backend/person`: `./gradlew ktlintCheck :app:api:test :app:api:bootJar`. Из `backend/person-worker`: `./gradlew ktlintCheck :app:worker:test :app:worker:bootJar`. На Windows используйте `gradlew.bat`. Из обоих frontend-приложений: `npm run check`, затем `npm run build`. Новый контракт генерируется командой `./gradlew generateClients :app:contract:api:openApiGenerate` из `backend/person`; после генерации переустановите локальные зависимости фронтендов через `npm ci`.

Игровые интеграции, динамическое расписание без короткого опросного такта, Redis и cursor описаны в [архитектуре](../game-integrations/ru.md).
